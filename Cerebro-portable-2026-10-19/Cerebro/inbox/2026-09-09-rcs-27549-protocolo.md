# RCS-27549 — Protocolo de prueba antes de avisar al cliente

Base: brain/memoria/reference_medir_lentitud_web_devtools.md. Aplica el mismo protocolo a dos pruebas separadas.

## Test 1. Primer load de un recibo en Work Item

1. Abre un Work Item de ICA con recibos que nadie haya tocado hoy. Evita el patron ya tibio del 376356.
2. Abre DevTools, pestana Network. Marca Preserve log. Confirma No throttling. Deja Disable cache desmarcado para la corrida tibia.
3. Haz clic en el primer recibo. Localiza el request xhr hacia instantanalytics event, columna Initiator.
4. En la pestana Timing de ese request, anota Waiting for server response.
5. Cierra el recibo. Abrelo de nuevo. Anota el TTFB del segundo intento. Debe bajar si el cache de disco sigue funcionando igual.
6. Repite con otros dos recibos del mismo Work Item. Toma la mediana de los tres primeros loads.
7. Guarda el HAR completo antes de cerrar DevTools, Save all as HAR with content.

## Test 2. Add Work Item to Investigation por numero de tienda

1. Toma cualquier Work Item, abre Add Work Item to Investigation.
2. Deja DevTools abierto desde antes del clic, Preserve log marcado.
3. Busca por numero de tienda. Usa 11789 y 14840, las mismas que fallaron en agosto.
4. Si la lista de investigaciones carga sin el error Something went wrong, anota el TTFB del request que trae los resultados.
5. Si el error reaparece, guarda el tracking code del modal y el HAR. El fix de recibos no cubre esto, es otro reporte para Engineering.

## Como decides

Si el test 1 baja de 3 a 8 segundos a algo cercano a un segundo, la migracion funciono para la carga de recibos. Si el test 2 sigue mostrando el error, el ticket no cierra ni se le dice al cliente que ya funciona todo, aunque el test 1 salga limpio.
