# RCS-27407 — Informe

PPG dejó de recibir Smart Alerts de auditoría SSVR desde el 6 de mayo de 2026. Ingeniería confirmó
un bug de código en ManageSmartAlerts.aspx como causa raíz. Shandana Khan autorizó el 1 de
septiembre que Support asuma el fix bajo ENG-8117, en Under Support Review, asignado a Luis
Hernandez.

## Qué reportó el cliente

Annie Brown, PPG, 2026-06-12, apertura del ticket:

"We recently added new audits with a slightly different title. We are not getting our Smart Alerts
when the users complete the audits. I believe this is something that needs an adjustment in the way
the file is listed."

## Qué se verificó

El estado en Jira hoy es Under Support Review. El assignee es Luis Hernandez. La prioridad es
Medium. El reporter es Annie Brown, cliente de PPG. No existe ficha previa de RCS-27407 en
`tickets/`, ni entrada en `bitacora/`, ni mención en `brain/markdown/` de SmartAlertConfig,
FiltersSQL o ManageSmartAlerts.aspx. Este ticket no tiene precedente propio en el cerebro. Todo lo
que sigue viene del hilo vivo de Jira.

Tyrone Whitney tomó el ticket el 2026-06-15 y en el call del 6/17 hizo un primer intento de
corrección directamente desde la UI de Manage Smart Alerts. Agregó los dos tipos de auditoría
nuevos al filtro existente y dio el ticket por resuelto en ese momento.

Annie Brown reportó el 2026-06-22 que las alertas seguían sin llegar. Store 9718 completó una
auditoría el 6/19 y no generó alerta.

Tyrone reabrió la investigación el 6/30 y el 7/2 confirmó la causa raíz con reproducción propia,
documentada en el ticket como nota interna:

"The Manage Smart Alerts page (ManageSmartAlerts.aspx) does not regenerate FiltersSQL when audit
type selections are modified and saved. The UI visually accepts the changes and displays them as
saved, but the underlying dbo.SmartAlertConfig.Filters and FiltersSQL columns remain unchanged."

La reproducción ocurrió dos veces, el 6/17 y el 7/2, con el mismo resultado ambas veces. Las ocho
alertas SSVR, SmartAlertConfigID 33 a 40, usan igualdad estricta contra el texto
`Structured Store Visit Report`. El tipo nuevo AuditConfigID 41,
`Structured Store Visit Report (US/PR)`, no matchea nunca contra esa igualdad. El tipo nuevo
AuditConfigID 40 para Canadá tampoco matchea, porque invierte el orden de las palabras a
`Store Structure Visit Report`. La última alerta disparada en todo el grupo fue el ConfigID 34 el
2026-05-06. Ningún config del 33 al 40 disparó desde entonces. El motor de alertas en sí funciona,
el ConfigID 45 de tareas sigue disparando a diario.

Tyrone escaló a Engineering el 7/2. Ryan Barlow confirmó internamente ese mismo día que el problema
es de producto y corresponde a Engineering, no a Delivery. Shandana Khan asignó el ticket el 7/3 a
Matthew Kamminga "for initial Engineering support as current SRE", pidiendo que se lo devolvieran a
ella para planning si requería investigación más profunda o resultaba ser un bug legítimo de
plataforma. El ticket quedó sin ticket ENG formal durante julio y agosto. Tyrone le confirmó a la
clienta el 7/31 que seguía siendo un "known issue" en trabajo, sin ENG creado todavía según su
propia nota interna de esa fecha.

El 2026-09-01 Matthew Kamminga escribió: "Please create new ENG ticket to handle. This would be a
good one to add to the support Queue." Shandana Khan respondió el mismo día: "Done - Support,
please use linked ENG-8117 to track any associated code changes." ENG-8117 existe hoy en estado
Backlog, tipo Story, mismo título que RCS-27407, y el mismo assignee, Luis Hernandez.

Aimee Wadsworth preguntó después, el mismo día: "is this an accepted in Dev ticket or is there
something more that Support needs to do?" Shandana Khan contestó de forma directa: "Support can own
the fix themselves (linking their code changes to the linked ENG ticket)."

Esa frase es la que Juan cita como punto de partida. No dice que este bug puntual ya se haya
resuelto antes. Aplica un proceso general ya documentado en el cerebro desde julio: la guía
"Making a Code Change - High Level Guide for Support", registrada en
`brain/markdown/24-appriss-dev-workflow-code-change.md`. Esa guía describe exactamente el patrón que
Shandana invoca. Un ticket RCS que requiere código se vincula a un ticket ENG. El RCS sigue siendo
la cara al cliente. El equipo de Support, en este caso vía Nuaav, ejecuta branch, build, PR, deploy,
QA y release bajo el número ENG. ENG-8117 cumple el rol de contenedor de tracking de código, no el
de ticket de desarrollo propio de Engineering. Backlog es coherente con eso, nadie de Engineering lo
va a tomar.

La regla de Shandana sobre comunicación al cliente, documentada en
`brain/markdown/19-rcs-procesos-playbook.md` a partir del caso RCS-28161, establece que Support
comunica un fix al cliente solo una vez que ese fix está en producción. Esa regla se escribió para
el flujo estándar donde Engineering hace el código y transiciona a Under Support Review al terminar.
Este ticket invierte el orden. Under Support Review aquí no significa que el fix ya esté en Prod,
significa que Engineering decidió que Support hace el código completo. El espíritu de la regla
sigue aplicando igual. No corresponde comunicarle a Annie Brown que esto está resuelto hasta que el
deploy a producción esté confirmado.

Sobre la vía de arreglo, `brain/memoria/reference_acceso_sql_tenants.md` fija la regla vigente para
cualquier acceso a base de datos de tenant vía Bastion y SSMS: "Todo lo que se corre en producción
es de solo lectura. Diagnóstico sí, cambios nunca." Tyrone dejó dos opciones en su investigación,
una corrección desde la UI y un UPDATE directo sobre SmartAlertConfig que requiere aprobación de
Dean o Constantine. La segunda opción queda descartada para Support bajo la regla de solo lectura.
El camino que sí queda abierto es corregir el bug de código y después re-guardar la configuración de
las ocho alertas desde la propia UI ya corregida, que es una escritura de aplicación, no un cambio
directo de base de datos.

Un dato pendiente de confirmar. La guía de code change en `brain/markdown/24` se documentó sobre la
plataforma moderna, con ejemplos de repos como Secure y pipelines de Azure DevOps bajo "Sysrepublic
Secure". El comentario técnico de Tyrone del 7/2 ubica esta app en netTrack legado, plataforma
`https://apps.lpguys.net/ppg/nettrack/`, base de datos con esquema `dbo` propio, no Platform
Cohesion. No hay evidencia en el cerebro de que el pipeline de Azure builds descrito en la guía
aplique igual a netTrack legado. Quien tome ENG-8117 necesita confirmar el repositorio y el pipeline
correctos antes de asumir que el flujo estándar de la guía corre sin cambios.

## Causa raíz

Confirmada. ManageSmartAlerts.aspx no regenera las columnas Filters y FiltersSQL de
dbo.SmartAlertConfig cuando se modifican y guardan las selecciones de tipo de auditoría en una
alerta ya existente. Afecta las ocho alertas SSVR, SmartAlertConfigID 33 a 40. Reproducida dos
veces por Tyrone Whitney, 6/17 y 7/2, mismo resultado ambas veces.

## Precedentes

No existe precedente específico de SmartAlertConfig, FiltersSQL o ManageSmartAlerts.aspx en
`tickets/`, `investigaciones/` ni `brain/markdown/`. El precedente que sí aplica es de proceso, no
de síntoma: `brain/markdown/24-appriss-dev-workflow-code-change.md`, guía Making a Code Change,
confirma que Support puede quedarse con la ejecución del código de un ticket que Engineering
triagea y decide no tomar directamente. La regla de comunicación al cliente de
`brain/markdown/19-rcs-procesos-playbook.md`, caso RCS-28161, sigue aplicando en espíritu aunque el
orden del flujo esté invertido en este ticket. La regla de solo lectura en producción de
`brain/memoria/reference_acceso_sql_tenants.md` descarta la opción de DB fix directo que Tyrone dejó
planteada como alternativa.

## Riesgo e impacto

El bug de ManageSmartAlerts.aspx no es exclusivo de PPG. Cualquier cliente que edite tipos de
auditoría en una alerta ya configurada sufre el mismo fallo silencioso, la UI confirma el cambio y
la base no lo aplica. Ryan Barlow señaló el 7/2 que no había visto el problema antes en otros
clientes. Tyrone lo reprodujo dos veces de forma independiente el mismo día que Ryan escribió eso.
Para PPG el impacto acumulado a hoy es de casi cuatro meses sin alertas de auditoría SSVR, desde el
2026-05-06. Afecta el seguimiento de action plans y de auditorías completadas para los tipos de
auditoría nuevos.

## Qué sigue

Luis Hernandez, assignee actual de RCS-27407 y de ENG-8117, ejecuta el fix de código bajo ENG-8117
siguiendo el flujo estándar de code change. Confirma primero el repositorio y pipeline correctos
para netTrack legado, porque la guía documentada no cubre explícitamente esa plataforma. El fix
corrige la comparación de tipo de auditoría para que use AuditConfigID en vez de igualdad de texto
contra el nombre. Una vez desplegado a producción, alguien del equipo re-guarda la configuración de
las ocho alertas SSVR desde la UI corregida para que el FiltersSQL se regenere. Support comunica a
Annie Brown solo después de confirmar con las queries de solo lectura que el filtro cambió y que
hubo al menos un disparo real posterior al re-guardado. El detalle ejecutable está en el instructivo
adjunto.
