Resolution summary, 9/28.

Issue:
From 9/24 11:06:43 UTC, Smart Alert runs for ADUSA, client 441, stopped completing. Runs reached "13a. Ready to send email" with no 13b, no insert into SmartAlertProcess and no End. InProcess stayed at 1, so every later save exited with "0. Quit ProcessSmartAlert because the smart alert for the case is still on processing". SmartAlertProcess had no rows after 9/24. Customer first noticed a case without alert around 4:20 PM ET on 9/24.

Checks along the way:
Infra, Russ Harmon on RETAILIT-20901, now Closed: SMTP relaying to SendGrid OK, API key valid, smartalert.email verified. SMTP now rejects emails over 25MB.
Kiran removed duplicate addresses from alert config 218 and manually triggered 9 cases on 9/27. The duplicates were not the cause.

Cause, per Kiran Vadday:
Deadlock in ProcessSmartAlert when processing runs in parallel under ADUSA traffic.

Fix:
PR 58273, one line change so a run waits for the previous one to finish. Validated in staging 9/27 23:56 UTC with 13b and a SmartAlertProcess row for ShopliftingID 1119654. Deployed to EU, then US prod on 9/28.

Verification:
Jim Cosseboom confirmed alerts from about 2:30 PM EDT 9/28. SmartAlertProcess rows with Success resumed from 19:30 UTC. Runs reach 13b and End.

Decisions:
Go forward only, requested by Jim and agreed with J.R. Teagle. The fix does not reprocess stuck cases. A save does not trigger them while InProcess = 1. Any resend is manual: reset InProcess, trigger ProcessCaseAlert.aspx, check Grafana and SmartAlertProcess.

Related: RCS-29026, RETAILIT-20901. Same pattern on Vitamin Shoppe, client 433, RCS-29145.
