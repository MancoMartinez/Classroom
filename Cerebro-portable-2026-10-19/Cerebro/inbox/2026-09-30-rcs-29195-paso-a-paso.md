## Parte C. La base, solo lectura

Paso 6. Entrar a la base del tenant
1. Abre Azure Bastion y conectate a SSMS.
2. Servidor: sqlmi-prd-wus2-arp-001. Login de lectura.
3. En una ventana nueva corre:
```sql
SELECT name FROM sys.databases WHERE name LIKE '%-387-%';
```
4. Debe salir una base con el patron sqldb-prd-wus2-arp-production-387-xxx-platform. ANOTA el nombre.
5. Seleccionala en el desplegable de bases o corre:
```sql
USE [sqldb-prd-wus2-arp-production-387-xxx-platform];
```
Cambia xxx por el codigo real.

Paso 7. Estado del caso en la base
Cambia <ID> por el ShopliftingID del paso 3.
```sql
SELECT s.ShopliftingID, m.CaseNo, s.InProcess
FROM incident.MasterCase m
JOIN incident.Shoplifting s ON s.MasterCaseID = m.MasterCaseID
WHERE m.CaseNo LIKE '%26-288-15%';

SELECT * FROM incident.SmartAlertProcess WHERE ShopliftingID = <ID> ORDER BY RunDate DESC;

SELECT TOP 20 * FROM incident.SmartAlertProcess ORDER BY RunDate DESC;
```
Que leer:
1. Primer query: el ShopliftingID coincide con el del paso 3. ANOTA InProcess. Si da error de columna, cambia m.CaseNo por s.CaseNo.
2. Segundo query: filas del caso. Sin filas confirma el paso 4.
3. Tercer query: si hay filas de hoy de otras alertas, el tenant envia alertas y el problema es de este caso o de esta alerta.

Configuracion de la alerta en la base:
```sql
SELECT * FROM incident.AlertConfig;
```
Ubica la fila de la alerta del paso 5. Compara su filtro guardado con lo que muestra la pantalla. Si difieren, es el mecanismo 1: la pantalla guardo y la base conserva el filtro viejo. No se corrige desde la pantalla.

Paso 8. Direcciones con salto de linea
```sql
SELECT AlertConfigID, EmailGroup FROM incident.AlertConfig
WHERE EmailGroup LIKE '%' + CHAR(13) + '%' OR EmailGroup LIKE '%' + CHAR(10) + '%';
```
Si sale la alerta de Property Damage, SendGrid descarta esas direcciones como Invalid.

## Parte D. Grafana, que paso cuando se guardo el caso

Paso 9. Abrir la consulta
1. Abre https://apprissretail.grafana.net y entra a Explore.
2. Datasource: grafanacloud-apprissretail-logs.
3. Cambia de Builder a Code.
4. Pega, con el ShopliftingID del paso 3:
```
{service_name=~".+", deployment_environment="usprod"} | clientId="387" |= "<ID>"
```
5. Rango: desde la fecha de creacion del caso del paso 3 hasta ahora. Grafana muestra hora Bogota. La base guarda UTC, cinco horas mas. Holly esta en ET, una hora mas que Bogota.
6. Run query.
No filtres por la palabra Property Damage. Trae el SQL de otras alertas y llena las 1000 lineas.

Paso 10. Buscar la linea de la alerta
1. Busca la linea 6a que trae el nombre de la alerta del paso 5.
2. Lee Rows Returned. Copia el SQL completo de esa linea, es el filtro real que corre.
3. Lineas salen desordenadas porque las alertas corren en paralelo. Ordena por hora.

Paso 11. Clasificar. Elige una rama

| Lo que ves | Rama | Que significa |
|---|---|---|
| Ninguna linea del ID | A | No hubo corrida. El caso no se guardo despues de crear la alerta, o no llego a la cola |
| Hay corrida pero ninguna 6a de la alerta | B | La alerta no se cargo para el caso: inactiva, fecha, tipo, plantilla. Vuelve al paso 5 |
| 6a con Rows Returned=0 | C | El filtro excluye el caso. Compara el SQL de 6a con los datos del paso 3 |
| 6a=1, 8, 8a, 11, 12b y nada despues | D1 | Cuelgue buscando adjuntos, mismo patron que Stater Bros 28534 |
| 13a sin 13b ni End, luego "0. Quit ProcessSmartAlert ... still on processing" | D2 | Atasco. Unica rama que se re dispara |
| 13b EMAIL SENT, 14 y End | E | Nettrack envio. El problema es entrega o destinatarios |
| Warning 16 | F | Adjunto o blob no encontrado |

Ramas A, B, C: causa de configuracion. Parte E.
Rama D1 o F: guarda las lineas de Grafana y escala con ellas. No dispares.
Rama D2: Parte F.
Rama E: pide a Russ Harmon el log de SendGrid por el asunto del correo. SendGrid guarda 7 dias. Revisa el paso 8.

## Parte F. Re disparar, solo rama D2

Esta parte es la guia de disparo manual de Kiran, la misma que uso Luis Hernandez y que segun Juan le funciono. Aqui va adaptada a 387 y gwmek. La guia misma dice que se usa solo para un caso atascado, asi que antes pasa por las Partes B, C y D.

Paso 13. Destrabar
1. En SSMS, con el login de escritura, sobre la base del paso 6:
```sql
SELECT ShopliftingID, InProcess FROM incident.Shoplifting WHERE ShopliftingID = <ID>;
UPDATE incident.Shoplifting SET InProcess = 0 WHERE ShopliftingID = <ID>;
SELECT ShopliftingID, InProcess FROM incident.Shoplifting WHERE ShopliftingID = <ID>;
```
2. El ultimo SELECT debe mostrar InProcess = 0. Guardar el caso con InProcess en 1 no dispara nada.

Paso 14. Disparar
1. En la pestaña de LPMS del paso 2, con sesion abierta en gwmek, pega:
https://apps.apprissretail.com/gwmek/nettrack/ProcessCaseAlert.aspx?ShopliftingID=<ID>
2. La pagina dispara sin guardar el caso. Envia correo real a la lista real de la alerta.
Si la ruta da error: con InProcess en 0, abre el caso y guardalo sin cambios. Es el metodo de Matt Kamminga.

Paso 15. Mirar Grafana
1. Misma consulta del paso 9, rango Last 15 minutes. Run query.
2. Bien: 6a Rows Returned=1, 8, 8a, 13a, 13b EMAIL SENT, 14, End.
3. Mal: 13a sin 13b, Quit, Warning 16 o 12b sin 13a. Para aqui. No repitas el UPDATE. Guarda las lineas y escala.

Paso 16. Confirmar
```sql
SELECT * FROM incident.SmartAlertProcess WHERE ShopliftingID = <ID> ORDER BY RunDate DESC;
```
1. Fila con RunDate de hoy en UTC y Success.
2. En LPMS, Smart Alert History del caso muestra el envio.
3. Success confirma que Nettrack envio, no que llego. Para la entrega, log de SendGrid con Russ Harmon.

InProcess = 1 solo no prueba atasco. El flag vale 1 mientras cualquier alerta corre.
No dar ETA a Holly ni prometer reenvio antes de terminar el paso 11.
